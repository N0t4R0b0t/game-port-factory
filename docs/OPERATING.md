# Operating the factory

## The short version

**You don't drive the CLI. You talk to Claude Code in this directory, and it drives the
CLI.** `CLAUDE.md` loads automatically and contains the session protocol, so the agent
already knows to read state first and hand off last.

Your actual jobs are four:

1. **Decide** — answer the judgement calls the agent brings you (strategy, scope cuts, art
   budget). These are the tasks tiered `opus` precisely because no machine can check them.
2. **Supply** — drop media you own into `ports/<slug>/source/`.
3. **Approve** — model pulls, anything that leaves the machine, anything destructive.
4. **Stop whenever you want** — the handoff makes that safe.

Everything else is the agent's job: reading state, picking the next task, delegating to
cheaper tiers, harvesting knowledge, writing the handoff, committing.

## Setup

Already done — the binary is symlinked onto `PATH`:

```bash
ln -sf ~/projects/game-port-factory/gpf/target/release/gpf ~/.local/bin/gpf
```

**Still to do**, if you want `gpf` to work outside the repo:

```bash
echo 'export GPF_ROOT=~/projects/game-port-factory' >> ~/.bashrc
```

Without it, `gpf` only resolves from inside the repo, by walking up to the `.gpf-root`
marker. With it, it works from anywhere.

After changing the CLI itself, rebuild — the symlink points at the release binary:

```bash
cargo build --release --manifest-path ~/projects/game-port-factory/gpf/Cargo.toml
```

## A session

**To start**, open Claude Code in this repo and say roughly:

> resume the fallout1-c64 port

or, for a fresh one:

> start a new port: Fallout 1 to C64

The agent runs `gpf status`, reads the handoff note from last time, reads `NOTES.md`, and
picks up. You do not need to remember where you were — that is the entire point of the
handoff discipline.

**To end**, say:

> wrap up

The agent runs `gpf harvest` (what did this session teach the factory?), `gpf handoff`
(what should the next session do first), and commits. A session that ends without this has
thrown away most of its value, because the next one starts cold.

If you just close the terminal, the work is still committed but the handoff note is stale.
Recoverable, not free.

## Naming places, not describing them

Every game gets `games/<game>/recipe/MAP.md` — a generated map with the room/level numbers,
their in-game names, what the port has built, and what is one step outside it. Read it
before a playtest and report bugs as **"room 52 (THE ENTRANCE HALL)"** rather than "the one
with the stairs". A description costs the agent a search and can match the wrong room; a
number cannot. It is regenerated by the port's own `tools/genmap.sh`, so it never goes
stale as more rooms get built.

## Matching work to the time you have

- **20 minutes** — answer pending decisions. Ask: *what decisions are you blocked on?* This
  is the highest-value use of a short session, because unblocking a decision unblocks hours
  of agent work you don't have to be present for.
- **A couple of hours** — a stage. Pick up wherever `gpf status` says and push to the next
  exit criterion.
- **A long stretch with quota to burn** — parallel fan-out. Say: *fan this out*. Breadth
  across independent verifiable tasks is where the token budget actually goes.

## Commands worth knowing yourself

Most of the CLI is for the agent. These four are genuinely useful to you:

```bash
gpf list                       # every port and where it stands
gpf status <slug>              # handoff note, blockers, next task
gpf plan c64,zxspectrum48,zx81 # what order to do targets in, and what carries between them
gpf models                     # local models: installed, what fits, what to pull
```

`gpf transfer <a> <b>` is worth a look when choosing the next target — it shows axis by
axis what you get for free and what has to be redone.

## What to expect the agent to ask you

It should bring you decisions, not tasks. If it's asking you to do mechanical work, that's
a routing failure worth pointing out. Legitimate questions look like:

- which strategy, given source availability and target capability
- how much detail to cut, and what the asset budget per category is
- whether a dead end is worth one more attempt or should be recorded and abandoned
- approval for a pull, an install, or anything that leaves the machine

## Reading the state yourself

Everything is plain text and greppable:

| File | What's in it |
|---|---|
| `ports/<slug>/PORT.toml` | stage, strategy, handoff note, blockers |
| `ports/<slug>/tasks.toml` | the task graph, with tier and verifier per task |
| `ports/<slug>/NOTES.md` | durable findings, format notes, **dead ends and why** |
| `ports/<slug>/SESSION-LOG.md` | append-only history |
| `factory/escalations.log` | which tasks were mis-tiered — the routing feedback |
| `factory/recipes/` | reusable decisions, each with its precondition |

## The one habit that matters

**Record dead ends with the reason.** Everything else in this system is convenience. An
unrecorded dead end gets retried in full by a session with no memory of the first attempt,
and that is the most expensive kind of forgetting available here.
